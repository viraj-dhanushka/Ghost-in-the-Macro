# Requirements Document

## Introduction

Feature 5 of the Kiroween feature set (source: `docs/KIRO_FEATURE_PROMPT_2026-11-25.md`, "Feature 5: Trial by Workbook, with a migration done by a Kiro agent"). The innovation claim: the original workbook, recalculated by LibreOffice, can referee anyone's rewrite, including code an AI agent wrote. The engine can already verify a hand-written `logic.py` and the MCP tool `verify_implementation` exists, but there is no named command, no example, and no migration in this repository that an agent carried out.

The feature has two parts. **Part A** is a named command, `ghost challenge`, and a line-up of suspect modules. **Part B** is a repair loop (a brief, a hook step, a skill section) and one real migration written by an agent and corrected by the workbook.

**Engine gate.** Part A needs a new module `ghost/challenge.py` and the registration of one subcommand in `ghost/cli.py`. That is an engine change beyond the one the Owner approved on 2026-11-26 (the single-line `If` fix). It is therefore **not built until the Owner approves it** (Requirement 12). Everything else in this feature lives outside `ghost/` and is built first.

Facts read from the code (2026-11-26), not assumed:

- `ghost verify <migration-dir>` verifies `logic.py` against the Referee. A `logic.py` that starts with `"""Generated by Ghost` is regenerated by the verifier; any other file is verified as hand-written code ("hand-written logic.py under test"). In that case the flip points and exact-hit cases still come from the transpiled module, which the report records in `boundary_notes`.
- A migration folder holds `rules.md` (one `## R-xxxxxxxx` section per rule: the EARS text, then a `Source:` line of cells), `traceability.yaml`, `findings.yaml`, `decisions.yaml`, `source.yaml` (the workbook path), `mapping.yaml` (inputs and outputs by name, with cell, type and minimum), `logic.py` and `reports/`. `ghost rules <workbook> --migration <dir>` writes the spec files and `source.yaml`.
- `proof-report.json` holds `mismatches[]` (each with `inputs`, `expected`, `actual`, `class`, and optionally `output`, `cell`, `rule_id`, `minimal`, `cases`), `cases_generated`, `cases_targeted`, `distinct_cases`, `seed` and `versions.libreoffice`.
- The verifier checks targeted boundary cases first and stops at the first mismatch no Decision explains; if a targeted case fails, the generated search does not run (`0 generated + 2 targeted` in a real failing run). Only a failure found in the generated search is shrunk by Hypothesis.
- `scripts/ghost_hook.py` dispatches the hooks in `.kiro/hooks/`; the hook `reverify-on-logic-save.json` runs `ghost_hook.py verify` when `logic.py` or `mapping.yaml` is saved under `.kiro/specs/<migration>/`. `tests/test_kiro_config.py` pins that hook's command.
- The Ghost MCP server exposes `analyze_workbook`, `list_rules`, `verify_implementation` and the other tools; `plugin/skills/implement-from-rules/SKILL.md` is the skill that tells an agent how to write `logic.py`.
- `graveyard/` is empty; `.gitignore` ignores `*.xlsx` and `*.xlsm`.

Baseline for this feature: after the VBA panel follow-up (local commit `1caf372`), the full suite reports 1603 passed, 3 skipped, 0 failed (370 s). `scripts/demo.sh` output is unchanged since the engine fix of 2026-11-26 (discount 31/33, haunted 33/35, D-001 Intended with one expected-by-decision mismatch at quantity 50).

## Glossary

- **Referee**: Headless LibreOffice recalculating the original workbook.
- **Candidate**: A module offered as the migration of a workbook, exposing `compute(inputs) -> dict`.
- **Suspect**: A Candidate shipped in `samples/suspects/` for the line-up.
- **Challenge**: A Faithful-mode verification of a Candidate against the Referee, with a printed verdict.
- **Line-up**: Running every Suspect of a workbook through the Challenge and writing `lineup.json`.
- **Repair brief**: `repair-brief.json`, written from a failed `proof-report.json`.
- **Repair log**: `repair-log.md`, one block per verification round of a hand-written `logic.py`.
- **Agent migration**: The folder `.kiro/specs/haunted-delivery-migration/`.
- **Baseline**: See the Introduction.

## Requirements

### Requirement 1: `ghost challenge` (engine gate)

**User Story:** As someone with a rewrite of a workbook, I want one command that tells me whether the workbook disagrees with it, so that I can judge the rewrite.

#### Acceptance Criteria

1. WHEN the Owner has approved the engine addition, THE `ghost` CLI SHALL provide `ghost challenge <workbook> --code candidate.py [--mapping mapping.yaml]`, implemented in a new module `ghost/challenge.py` with one subparser and a three-line `cmd_challenge` in `ghost/cli.py`.
2. THE command SHALL verify the Candidate against the Referee in Faithful mode, on a temporary migration folder, and SHALL NOT modify the workbook, the Candidate or any migration's `reports/` folder.
3. IF the Candidate starts with the generated-code marker, THEN THE command SHALL refuse with a message that it would be regenerated, and SHALL NOT verify it.
4. THE command SHALL print: cases generated, targeted and distinct; the seed; the LibreOffice version; and either "no difference found on N cases" or one counterexample.
5. THE counterexample SHALL show the inputs, the Referee value, the Candidate value, the output cell, the rule id and the EARS rule text, and SHALL write "not available" for a rule id or text the report does not have.
6. THE command SHALL print "shrunk" only when the counterexample came from the Hypothesis search, and "targeted boundary case, not shrunk" when a targeted case failed first.
7. THE command SHALL exit 0 (no difference) or 1 (a difference) only when a proof report was written, and SHALL exit 2 in every other case (workbook not found, mapping file not found, Candidate file not found, unreadable, a syntax error, an import that raises or calls `sys.exit`, no `compute`, a candidate result that lacks a mapped output name or holds `None` for it ("candidate did not return output <name>"), the Referee unavailable, the report not written, a generated-code refusal), with one line on standard error giving the reason. THE command SHALL catch `SystemExit` around the Candidate load and around the run, and any `BaseException` at the top, so that exit 1 always means a report exists. A `compute` that raises is a difference once a report was written: exit 1, with the failing input and the exception shown.
8. THE output SHALL NOT contain the words "correct", "proven" or "proved".
9. THE command SHALL NOT run a macro and SHALL accept a macro workbook only with the engine's existing macro handling (macros off).
10. WHEN `--out DIR` is given, THE command SHALL keep the migration folder and the proof report in DIR (which SHALL NOT exist or SHALL be empty, otherwise exit 2); without it the folder SHALL be temporary and removed.
11. WHEN `--mapping` is omitted, THE command SHALL derive the mapping from the workbook and SHALL print that the mapping was not confirmed by a person, with the input and output names and cells.
12. THE command SHALL capture the output of `ghost verify`'s run so that no absolute path of the temporary folder appears in its own output.
13. THE command SHALL NOT be reachable from `web/` or from a new MCP tool; a test SHALL fail if anything under `web/` imports `ghost.challenge` or `load_compute`.
14. `--help` and the README SHALL say that the command runs the Candidate's code on this machine and that a Candidate that loops will hang it.
15. THE command is additive: THE verifier, the report schema and every existing command SHALL be unchanged. Left for Feature 7: a receipt file, `--trust-macros`, an engine-written repair brief.

### Requirement 2: Suspects and the line-up

**User Story:** As a viewer, I want to see the workbook convict a wrong rewrite and clear an honest one.

#### Acceptance Criteria

1. THE repository SHALL hold `samples/suspects/haunted/` and `samples/suspects/discount/`, each with a pinned `mapping.yaml` and three or four Candidate modules: an honest translation, a `>` versus `>=` slip, float rounding in place of Excel rounding, and a dropped branch (the haunted set also holds a "tidied" translation that removes the workbook's own inconsistency).
2. EVERY Suspect SHALL be run through the Referee before it is labelled. A Suspect that the Referee does not catch SHALL be reported as "no difference found on N cases" and its label SHALL be corrected to say so; no label SHALL be shipped that a run contradicts.
3. EACH Suspect's header SHALL say truthfully how it was written. A header SHALL claim AI authorship only if the prompt that produced it is committed beside it.
4. THE line-up SHALL write its own `lineup.json` (suspect, exit code, verdict line, counterexample inputs when there is one, seed, LibreOffice version) and SHALL NOT write into a migration's `reports/` folder.
5. THE honest Suspect SHALL never be convicted, across several seeds.
6. EVERY reported counterexample SHALL reproduce: re-evaluating the same inputs on the Referee and on the Suspect SHALL give the reported values.

### Requirement 3: The repair brief

**User Story:** As an agent repairing a rewrite, I want the smallest evidence of what is wrong.

#### Acceptance Criteria

1. A new script `scripts/repair_brief.py` SHALL read a migration folder's existing `proof-report.json` and `rules.md` and write `repair-brief.json`, and SHALL change no engine code.
2. WHEN the report passed, THE brief SHALL be `{"status": "passed"}`.
3. WHEN the report did not pass, THE brief SHALL hold the minimal failing mismatch (the one marked `minimal`, else the first that is not expected by decision): its inputs, the Referee value, the actual value, the output cell, whether it is a targeted boundary case or a shrunk search case, and the rule id with its EARS text and source formula; `rule_text` and `source_formula` SHALL be "not available" when the rule id is missing or the text cannot be found.
4. THE brief SHALL contain no value that is absent from the report it was built from (apart from the rule text and the source formula, which come from `rules.md` and the workbook) and no absolute path.

### Requirement 4: The repair step in the hook

**User Story:** As the Owner, I want each verification round of an agent's module recorded, so that I can see what happened.

#### Acceptance Criteria

1. THE dispatcher `scripts/ghost_hook.py` SHALL gain a `repair` kind, and the existing `verify` kind SHALL call it after verification, so that the existing hook on `logic.py` saves is the only hook on that path and `.kiro/hooks/reverify-on-logic-save.json` is unchanged.
2. WHEN `logic.py` in the migration folder is hand-written (not Ghost-generated), THE repair step SHALL write the repair brief and append one block to `repair-log.md`: round number, time, seed, cases, pass or fail, and the counterexample.
3. WHEN `logic.py` is Ghost-generated or missing, THE repair step SHALL do nothing extra.
4. THE repair log SHALL be written by the script from the proof report, and SHALL NOT be edited by hand or by any other step; after five failed rounds without a pass the block SHALL say "not converged".
5. A planted bug SHALL be labelled "planted" in the log only through an explicit, visible option of the repair step (an environment variable naming the plant), never inferred.

### Requirement 5: The skill

**User Story:** As an agent, I want rules for how to repair.

#### Acceptance Criteria

1. `plugin/skills/implement-from-rules/SKILL.md` SHALL gain a "Repair loop" section: read `repair-brief.json`; change only what it demonstrates; never touch the workbook, `mapping.yaml`, `decisions.yaml` or the tests; stop at "not converged".

### Requirement 6: The agent migration

**User Story:** As a judge, I want to see a migration that an AI agent carried out and the workbook checked.

#### Acceptance Criteria

1. THE haunted sample workbook SHALL be in `graveyard/haunted.xlsx`, generated by `samples/make_haunted.py`, with a `.gitignore` exception so it is committed.
2. THE folder `.kiro/specs/haunted-delivery-migration/` SHALL hold the rules, traceability, findings, an agent-written `logic.py` (no generated marker) and `mapping.yaml`, `repair-log.md`, `repair-brief.json`, the proof report, and the prompt that produced the agent's files.
3. THE agent SHALL write `logic.py` from the rules spec alone, using only the Power's skills and the Ghost MCP tools or CLI as available, and what it could and could not use SHALL be recorded.
4. THE migration SHALL be Faithful only.
5. THE repair log SHALL record what really happened. IF the agent's first attempt passes, THEN THE log SHALL say so; to show the loop working, one bug MAY then be planted, labelled "planted" in the log and in the usage log, and the loop SHALL find and repair it.
6. NO agent file SHALL claim a result the log does not show.

### Requirement 7: Correctness properties

#### Acceptance Criteria

1. Property 1: an honest Suspect is never convicted, across several seeds (Referee-backed test).
2. Property 2: every counterexample reported by the line-up reproduces on the Referee and on the Suspect (Referee-backed test).
3. Property 3: the repair brief contains no value that is absent from the report it was built from, and no absolute path (Hypothesis over schema-valid reports, no LibreOffice).
4. Properties are tagged `# Feature: trial-by-workbook, Property N: <title>`.

### Requirement 8: Optional web line-up (stretch)

#### Acceptance Criteria

1. IF time remains, THE Web_App MAY show a read-only line-up that runs only the Suspects shipped in the repository, says so on the page, and returns 409 for uploaded workbooks; THE public server SHALL NEVER run code supplied by a visitor.

### Requirement 9: Constraints and invariants

#### Acceptance Criteria

1. THE feature SHALL leave the Demo_Invariants unchanged: discount Faithful passes with mutation at least 31/33; haunted raises F-001, Faithful passes with 0 mismatches and mutation at least 33/35; haunted with D-001 in Intended mode passes with exactly one "expected by decision" mismatch at quantity 50 (Referee 6.0, new code 0); seed 20261204; default cells `Calculator!B2,B3,B4` to `B11` and scenarios `Model!B2,B3,E2` to `B19,B20`.
2. THE feature SHALL leave all existing tests passing and SHALL add only new tests; the full suite SHALL show the Baseline plus only this feature's new tests, with 0 failed.
3. THE feature SHALL add no runtime dependency and SHALL NOT change the `proof-report-1` schema.
4. A check that was not run SHALL read "not checked"; no label, log line or brief SHALL carry a value the engine did not produce.
5. THE feature SHALL NOT run a macro and SHALL NOT run code supplied by an upload.
6. THE feature SHALL leave its changes uncommitted until it is done, then commit locally and SHALL NOT push.

### Requirement 10: Honesty of the agent record

#### Acceptance Criteria

1. `repair-log.md` SHALL be produced only by `ghost_hook.py repair`; the committed log SHALL be the one the script wrote.
2. THE usage log SHALL say who wrote each agent file, with what context, and what that context could have leaked (the agent session that had seen the workbook), and SHALL record every failed or discarded attempt.

## Known limits

- **The agent is not independent of this repository.** The agent runs inside the same Kiro workspace; it is told to use only the rules spec, but the repository (including the generated modules and tests) is readable. The prompt forbids reading them, and the record says what the agent actually opened where that is known; it is not enforced.
- **A hand-written module has no trace hook**, so Intended mode cannot attribute a mismatch to a Decision (Requirement 6.4).
- **Boundary cases come from the transpiled module**, not from the Candidate (the report says so in `boundary_notes`).

## Out of scope

- Running any code supplied by a web visitor.
- Intended mode for an agent-written module.
- Changing the verifier, the report schema or the engine's rounding.
