# haunted-delivery-migration

A migration of `graveyard/haunted.xlsx` (generated by `samples/make_haunted.py`) in which the module was written
by an AI agent and checked by the workbook, recalculated by LibreOffice. Faithful mode only: an agent-written
module has no trace hook, so Intended mode cannot attribute a mismatch to a Decision (the D-001 story stays with
the generated-module demo).

## What is here and who wrote it

| File | Written by |
|---|---|
| `rules.md`, `traceability.yaml`, `findings.yaml`, `design.md`, `source.yaml` | `ghost rules graveyard/haunted.xlsx --migration .kiro/specs/haunted-delivery-migration` (the engine). The same rule ids and text were returned by the Ghost MCP tool `list_rules`. |
| `logic.py`, `mapping.yaml` | A fresh agent session, from `rules.md` and the constants it read through the Ghost MCP tool `evaluate_original` (`rules.md` names constants by cell, not by value), with the prompt in `agent-prompt.md`. `mapping.yaml` was rewritten in round 2 by a second fresh session (`agent-prompt-round-2.md`). |
| `repair-log.md`, `repair-brief.json`, `proof-report.json`, `proof-report.html`, `reports/` | `scripts/ghost_hook.py verify`, which runs `ghost verify` and then `scripts/ghost_hook.py repair`. Not edited by hand. |
| `agent-prompt*.md` | The repository owner's assistant. Each is the whole instruction the agent got, plus a one-line pointer to the file. |

The docstring at the top of `logic.py` says "written by hand". It is the agent's own wording and is left as it was
written; the module was written by an AI agent session, not by a person.

## What happened, round by round (the log is `repair-log.md`)

- **Round 1, FAIL.** The first agent wrote `logic.py` and a `mapping.yaml` without input types or minimums. The
  skill's mapping example (a plain `quantity: Sheet1!B2`) was in a format the engine rejects and showed no
  domains; the agent found the working shape from the engine's error. The search then tried negative prices and a
  fractional quantity, where the Referee's binary floating-point result differs from exact Decimal arithmetic by
  about 2e-6 at a magnitude of 1e10 (over the 1e-6 tolerance). The agent did not change `logic.py` and asked for a ruling.
- **Round 2, PASS.** `agent-prompt-round-2.md` says "the user confirms" the input domains (quantity an integer,
  minimum 0; the other two decimals, minimum 0). That is not accurate: no human was asked. The repository owner's
  assistant supplied the values that `ghost convert` writes into its own generated mapping for this workbook, and
  the Owner has not confirmed them. The pass covers the tested domain, 0 to 10000 for each input
  (`tested_domains` in `proof-report.json`); negative and unbounded inputs are not tested. A second fresh session
  changed only `mapping.yaml` to declare the domains; `logic.py` was not changed (same
  SHA-256 before and after: `058494df6abee8bf238fd402d8346e358bf81055fbfbe3e6dcc65867aa9708ff`).
- **Round 3, FAIL (planted).** To show the loop working, the free-delivery comparison in `logic.py` was changed from
  `>` to `>=` by the repository owner's assistant. The log labels this as planted. The Referee caught it at the
  targeted boundary case, quantity 50 (Referee 1084.26, module 1077.30).
- **Round 4, PASS.** The repair demonstration was not blind: `agent-prompt-round-3.md` tells the agent that the
  failure is a planted test bug. A third fresh session read `repair-brief.json`, `rules.md` and `logic.py` (and was told not to
  open the log, whose "planted" line states where the change was), and changed one line back. The final `logic.py`
  is byte-for-byte the one from round 2.

The skill was corrected afterwards (a mapping example the engine accepts, with `type` and `min`, and a rule that
`mapping.yaml` changes only when the user asks).

## Which tools each session used (from the sessions' own reports; the reports are not committed)

- Round 1 session: MCP `evaluate_original` (two calls: one rejected for an empty `inputs` object, one reading
  `Calculator!E2` to `E7`), MCP `verify_implementation` (one call), and shell commands (the hook command twice; the
  first crashed on the mapping format and wrote no log block).
- Round 2 session: shell commands only (no MCP tool).
- Round 3 session: shell commands only (no MCP tool). It opened `repair-brief.json`, `rules.md` and `logic.py`, not
  `repair-log.md`.

## Limits

- The log is written only by `ghost_hook.py repair`, but nothing enforces that: a person could edit or delete the
  file, and the round count and the "not converged" rule read it. The header says not to edit it.
- Only the final `repair-brief.json` is committed (`{"status": "passed"}`); each failed round's counterexample is
  in the log, but the failed briefs themselves were overwritten.
- The report says "mutation: not checked" (no mutation self-check was run on this migration).

- The agents are not independent of this repository: they ran in the same workspace and could read other
  files. The prompt forbids it and each session reported what it opened; nothing is enforced. The first session
  saw a traceback that printed a few lines of engine source by accident.
- The brief names the rule linked to the output cell (`R-794f519c`, the total), not the rule that holds the
  planted change (`R-5f32fa17`); the agent worked that out from the numbers.
- The Referee run says "not cross-checked against Excel": there are no Excel-saved values in the sample.
- Boundary cases come from the transpiled module, not from `logic.py` (the report says so).
